## 2. Методика

Агент выполняет статическое ревью: (1) извлекает текст с номерами строк; (2) выделяет требования (моделью), каждая цитата сверяется с исходным текстом; (3) формальные правила ищут заглушки, пустые поля, размытые термины, требования без идентификаторов; (4) модель проверяет каждое требование по критериям C1–C9 и (5) набор целиком по S1–S8; (6) цитата каждого дефекта ищется в документе — дефект без подтверждённой цитаты в отчёт не попадает; (7) итог: есть критичные → «НЕ ГОТОВ»; часть проверки не выполнена → «ПРОВЕРКА НЕ ЗАВЕРШЕНА»; есть значительные → «ГОТОВ С ОГОВОРКАМИ»; иначе «ГОТОВ».

Шкала критичности:
- «критичный» — без исправления нельзя однозначно реализовать или протестировать: противоречие, непроверяемость, неполнота ключевого поведения, ошибка, ведущая к неверной реализации.
- «значительный» — высокий риск разного толкования или пропуска сценария, но основной путь реализуем.
- «незначительный» — оформление, стиль, прослеживаемость, не влияющие на поведение системы.

  - «{"result":"ERROR","message":"Проверьте сумму"}» — Часть B. REST API › Статусы › 200. Successful — Created, строка 171
  - «Если результат 200 или 201 — успешный. Если результат 400, 401 и далее — неуспешный.» — Часть B. REST API › Ответ, строка 151
  - «200. Successful — Created» — Часть B. REST API › Статусы › 200. Successful — Created, строка 165
- Требования: R-28, R-45, R-47, R-39, R-46, R-44, R-51
- Суть: Отклонение суммы описано двояко. Логика (п. 5) и пример возвращают result=ERROR со статусом 200, а статус 400 предназначен для неверных параметров, то есть для той же ситуации. Раздел «Ответ» считает успешными 200 и 201, но 201 нигде не описан. Пример 200 назван «Successful — Created», хотя Created соответствует 201. Тело ответа 400 не содержит поля result. Клиент не может однозначно определить исход по статусу.
- Рекомендация: Принять одно правило: ошибки валидации — всегда 400 с единым телом, успех — 200 (или 201 для создания). Убрать result=ERROR со статуса 200. Исправить заголовок «Successful — Created» и привести таблицу ответа в соответствие со всеми статусами.

## 7. Итог

**Решение: НЕ ГОТОВ**

- **Разработка:** Начинать разработку нельзя: есть 4 критичных противоречия. Месяц покупки в Ф-2 конфликтует с критерием приёмки 2 (D-054), Ф-3 расходится с Ф-4 по повторному push (D-055), saveLimit описан как GET и как «чтение» (D-056), а модель ошибок 200/ERROR, 400 и 201 неоднозначна (D-057). Кроме того, не определены термины «проведённая покупка» и «сумма» в push (D-013, D-022, D-058), граничные состояния порога (D-063), отказы интеграций и идемпотентность (D-064, D-026), а также URL Prod (D-029, D-072).
- **Тестирование:** Писать тест-кейсы рано: ожидаемый результат неоднозначен там, где противоречат друг другу требования и критерии (D-054, D-055, D-057, D-042, D-051). Не определены поведение при enabled=0 (D-044, D-060), реакция на чужую или неподходящую карту (D-031, D-041, D-061, D-067) и содержимое push (D-022, D-058). Критерии приёмки покрывают малую часть требований, раздел «Тестирование требований» пуст (D-065, D-070), а срок в минуту невозможно проверить без точки отсчёта и перцентиля (D-001, D-023). Можно заранее подготовить только тест-дизайн для диапазона порога 1 000–1 000 000 при условии, что будет выбрана единая реакция на ошибку.
